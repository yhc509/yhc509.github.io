# 프레임 타임

## 한 장이 16ms를 넘기면 어디부터 볼까

초안이다. 공개 목록에는 올리지 않는다.

---

###### 기준

# 예산. 화면이 요구하는 시간

60Hz면 한 프레임의 예산은 16.6ms다. 30Hz면 33.3ms다.

- **측정** 평균이 아니라 상위 1% 프레임을 본다
- **구간** CPU 시뮬레이션, 렌더 제출, GPU 대기를 나눈다
- **흔들림** 평균이 맞아도 간헐적인 긴 프레임이 보인다
- **입력** 긴 프레임은 입력 지연으로 이어진다
- **기록** 같은 장면, 같은 카메라, 같은 해상도로 비교한다

---

###### CPU

# 메인 스레드. 시뮬레이션이 예산을 먹는 경우

프레임 시작부터 렌더 제출까지를 먼저 자른다.

- **스크립트** 씬 전체 순회가 매 프레임 돌면 길어진다
- **물리** 콜라이더 수가 늘면 브로드페이즈가 커진다
- **애니메이션** 본 수가 많은 캐릭터가 화면에 겹친다
- **할당** 프레임 중간의 할당은 뒤늦은 수집으로 튄다
- **로그** 개발 빌드의 로그가 릴리즈와 다른 시간을 만든다

---

###### GPU

# GPU. 제출은 빨라도 화면에 늦는 경우

CPU가 놀고 GPU가 바쁘면 다음 프레임이 큐에서 기다린다.

| 신호 | 의미 | 다음에 볼 곳 |
| --- | --- | --- |
| GPU 시간 증가 | 셰이딩 또는 대역폭 | 오버드로, 해상도 |
| CPU 대기 | 펜스에 막힘 | 읽기 되돌림, 동기화 |
| 버텍스 증가 | 장면이 무거움 | 컬링, LOD |
| 드로우 증가 | 배칭이 깨짐 | 재질, 인스턴싱 |

- 숫자를 한 장면으로 고정한 뒤에 항목을 하나씩 뺀다

---

###### 순서

# 줄이는 순서. 큰 것부터 하나

한 번에 여러 개를 고치면 무엇이 줄었는지 알 수 없다.

1. **캡처** 긴 프레임 하나의 타임라인을 남긴다
2. **가장 긴 구간** 그 구간만 반으로 줄이는 실험을 한다
3. **다시 측정** 상위 1%가 줄었는지 확인한다
4. **다음 구간** 예산 안으로 들어오면 다음으로 넘어간다

> 초안이다. 수치는 예시가 아니다.

###### 함정

# 평균에 속지 않기

평균 프레임 타임이 예산 안이어도 플레이는 버벅일 수 있다.

- **히치** 로딩, 셰이더 컴파일, 첫 사용 리소스가 한 프레임에 몰린다
- **웜업** 측정 전에 같은 장면을 한 바퀴 돌린다
- **창 모드** 포커스를 잃으면 프레임 제한이 달라진다
- **전원** 배터리 절전이 켜지면 같은 빌드가 다르게 나온다
